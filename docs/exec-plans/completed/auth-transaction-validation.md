# 인증·검증·거래 조회 안정화

## 범위와 완료 조건

- Android 앱이 미사용 시간과 관계없이 유효한 Refresh Token을 사용해 세션을 복구한다.
- Access Token 만료 시 한 번만 Refresh rotation을 수행하고, Refresh Token이 만료·폐기된 경우에만 로그인 화면으로 이동한다.
- Refresh Token 유효기간은 30일로 운용하고 앱은 회전된 토큰을 암호화 저장한다.
- 상품 등록·수정의 출시년도는 미입력을 허용하되 1900년 미만이면 `400 INVALID_RELEASE_YEAR`로 거절한다.
- 경매 시작가와 입찰가는 양수인 10원의 배수만 허용하며 REST와 WebSocket 경로에 같은 검증을 적용한다.
- 환불 커밋 후 구매자 실시간 알림을 발행하고 앱이 주문 목록·상세를 다시 조회한다.
- 판매자의 예정·진행·낙찰·유찰·취소 경매가 판매 내역에 표시된다.
- 구매 거래 상세에 대표 이미지 `product.thumbnailUrl`이 일관되게 반환되고 앱에 표시된다.
- Toss 빌링키 발급 오류를 내부 오류 코드와 사용자 메시지로 매핑하고 앱에서 재시도할 수 있다.
- 변경 범위의 백엔드·프론트엔드 테스트를 통과한다.

## 영향 컴포넌트

- Frontend: 세션 수명주기, 환불 실시간 반영, 거래 조회 화면, 결제수단 등록 오류 처리
- Backend: JWT 설정, 입력 검증, 환불 이벤트·알림, 판매/구매 조회, Toss 오류 매핑
- Orchestration: 실행 계획과 통합 검증 결과

## 결정 기록

- 앱의 30분 미사용 강제 로그아웃은 제거하고 Refresh Token 유효성에 세션 수명을 맞춘다.
- Access Token 자동 갱신은 동시 요청을 단일 갱신으로 합치고 원 요청을 한 번만 재시도한다.
- 출시년도 1900은 허용하며 미래 연도 상한은 이번 범위에서 추가하지 않는다.
- `등록가`는 경매 `startPrice`를 의미하며 `marketPrice`는 10원 단위 검증 대상에서 제외한다.
- 시작가와 입찰가 모두 0원을 허용하지 않고 10원의 배수로 제한한다.
- 판매 내역은 주문 생성 여부와 무관하게 판매자가 등록한 모든 경매를 대상으로 한다.
- 구매 상세 이미지는 응답 계약을 확장하지 않고 기존 `thumbnailUrl` 계약을 바로잡는다.
- Toss 원문 오류는 사용자에게 직접 노출하지 않고 서버 오류 코드와 앱 사용자 메시지로 변환한다.

## 검증 결과

- 작업 시작 시 orchestration, backend, frontend, AI가 각각 `origin/develop`과 동일함을 확인했다.
- infra의 현재 커밋이 `origin/develop`과 동일함을 확인했다.
- Backend 핵심 테스트 7종을 실행해 성공했다.
- Frontend `:app:testDebugUnitTest`, `:app:lintDebug`, `:app:assembleDebug`가 성공했다.
- Backend 전체 테스트는 작업 전후 동일하게 2건 실패했다. 로컬 PostgreSQL 미기동과 기존 Flyway V6 중복 마이그레이션이 원인이며 이번 변경과 무관하다.
- Backend와 Frontend 모두 `git diff --check`를 통과했다.

## 후속 확인

- 실제 Toss 장애 당시 화면 영상, Android 로그, 백엔드 로그와 API 요청·응답은 제공되지 않아 실결제 환경의 빌링키 발급 성공 여부는 별도 확인이 필요하다.
- orchestration에 기존 AI submodule 포인터 변경이 staged 상태로 존재하며 이번 작업에서는 수정하거나 커밋하지 않는다.
